# employee-react-vite 

---

## JSX가 뭔지

자바스크립트는 원래 변수, 함수, 조건문, `fetch` 같은 문법만 쓴다.

**JSX**는 그 위에 HTML이랑 비슷한 태그를 섞어 쓰는 문법이고, 파일 확장자가 보통 `.jsx`다. 리액트에서 "화면 한 덩어리"를 함수로 만들 때 이 안에 JSX를 쓴다.

```jsx
function Hello() {
  return <h1>안녕</h1>;
}
```

브라우저는 JSX를 그대로는 못 읽고, **Vite** 같은 빌드 도구가 돌면서 일반 자바스크립트로 바꿔준다.

정리하면, **`.jsx` = 리액트 컴포넌트(화면 조각)를 적는 파일**이라고 보면 된다.

---

## 이 프로젝트가 하는 일

한 줄로 말하면 **직원(Employee)이랑 부서(Department)를 목록으로 보고, 검색하고, 등록·수정·삭제하는 웹 화면**이다.

데이터는 백엔드랑 통신하는데, 그 요청을 모아둔 게 `src/api/` 아래 `employeeApi.js`, `departmentApi.js`다. (여기는 JSX 아니고 그냥 JS.)

---

## 폴더·파일 역할

| 경로 | 내가 붙인 설명 |
|------|----------------|
| `src/main.jsx` | 앱 진입점. DOM에 리액트를 꽂고 `App`을 띄운다. |
| `src/App.jsx` | 전체 레이아웃, 탭(직원/부서), 토스트 같은 **큰 그림**. |
| `src/components/employee/` | 직원 쪽 화면 조각들 |
| `src/components/department/` | 부서 쪽 화면 조각들 |
| `src/components/common/Toast.jsx` | 알림(토스트) UI |
| `src/api/*.js` | 서버 주소로 요청 보내는 함수들 |
| `src/index.css`, `style.css`, `App.css` | 스타일 (Tailwind 등) |
| 루트의 `vite.config.js` | 개발 서버·빌드 설정 |

### 파일 이름 패턴 (이 프로젝트에서)

- **`SomethingSection.jsx`** — 그 메뉴(직원/부서)에서 **상태랑 API 호출을 모아두는 상자**
- **`SomethingList.jsx`** — **표/목록**만
- **`SomethingForm.jsx`** — **입력 폼**만
- **`SomethingSearch.jsx`** — **검색**만

---

## 코드 읽는 순서

1. `main.jsx` → `App.jsx` 순으로 "어디서 시작해서 화면에 뭐가 뜨나"만 따라가 본다.
2. 그다음 **직원**이면 `EmpSection.jsx` 하나만 파고, 거기서 어떤 컴포넌트를 불러오는지 본다.
3. 화면 한 조각만 궁금하면 `EmpForm.jsx`처럼 **파일 하나만** 연다.

한 번에 전부 이해하려 하지 말고, **진입 → 큰 컨테이너(Section) → 작은 조각** 순이 덜 막힌다.

### 상태 관리 라이브러리(Redux, Zustand 등)를 꼭 써야 하나?

**아니다.** 작은·중간 규모는 `useState`, `useReducer`, 필요하면 `useContext`만으로도 충분한 경우가 많다.

별도 라이브러리는 보통 **앱이 커졌을 때** 여러 화면이 같은 데이터를 공유하거나, props를 깊게 넘기기 싫을 때 고려한다. 전역 상태·변경 흐름을 한곳에 두고 싶을 때 Redux 계열, 가볍게 쓰고 싶을 때 Zustand 같은 선택을 한다. **필수 과목이 아니라 규모·팀 상황에 맞는 도구**로 보면 된다.

### `document.getElementById`로 DOM 직접 건드리면 왜 안 좋나?

React는 **화면을 “상태(state)에 따라 그린다”**는 모델이다. 리액트가 만든 DOM을 `getElementById`로 직접 바꾸면, **다음 렌더에서 리액트가 다시 그리면서 덮어쓰거나** 실제 화면과 내부 상태가 **어긋나기 쉽다**. 그래서 동적 처리도 가능하면 **state를 바꾸고 JSX가 그에 맞게 그리게** 하는 게 기본이다. (차트·지도처럼 외부 라이브러리가 DOM을 잡는 경우는 `ref`/`useEffect`로 “그 구역만” 다루는 패턴이 있다.)

### 상태 관리 도구 간단 비교

| 이름 | 특징 | 장점 | 단점 |
|------|------|------|------|
| **Redux Toolkit** | 예측 가능한 전역 스토어, 액션·리듀서 패턴 | 도구·자료 많음, 큰 팀·복잡한 규칙에 적합 | 보일러플레이트·학습 비용 큼 |
| **Zustand** | 최소 API, 스토어가 함수 형태 | 가볍고 배우기 쉬움 | 매우 규모 큰 팀에서 패턴 통일은 팀 규칙 필요 |
| **Jotai / Recoil** | “원자(atoms)” 단위 상태 | 잘게 나눠 쓰기 좋음 | 개념 익숙해지는 데 시간 |
| **Context API** | 리액트 내장, Provider로 감싸기 | 추가 설치 없음 | 자주 바뀌는 값에 남발하면 불필요한 리렌더 |

### `.js` 말고 `.jsx`를 쓰는 이유

- **JSX 문법**(`<div>`)이 들어가는 파일임을 **이름만 보고 구분**하기 쉽다.
- 에디터·빌드 도구가 **파싱·하이라이트**를 맞추기 좋다.
- 기술적으로 `.js`에도 JSX를 넣을 수 있지만(설정에 따라), **관례적으로 UI 컴포넌트는 `.jsx`**, 순수 로직·API는 `.js`로 나누는 경우가 많다.

**장점 요약:** 파일 역할이 분명해지고, 팀·도구와 맞추기 쉽다. JSX는 HTML처럼 “화면 구조”를 한눈에 읽기 쉽게 쓰게 해 주는 문법이다.
